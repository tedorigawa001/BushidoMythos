# GPU 最適化ベンチマークで踏んだ3つの罠 — 「速くならない」より怖いのは「正しく測れていない」

## TL;DR

- 自作 LLM(98.6M Recurrent-Depth Transformer)の学習を A100 で約 2.3 倍に高速化する過程で、**測定そのものを誤る罠を3回踏んだ**。いずれも「ベンチは正常な数字を返すのに、その数字が主張を支えていない」タイプ。
- **罠①: コンパイル代の計測混入** — torch.compile が「2.2 倍遅い」と出たが、実際は動的制御フローが生む再コンパイルが計測区間に漏れていた。定常状態では 1.075 倍速。
- **罠②: silent fallback** — grouped GEMM 経路が dtype 判定で静かに無効化され、**旧実装をもう一度測っただけ**の結果を「効果なし」と読みかけた。peak VRAM の MiB 単位一致と loss 差の 8 桁一致が決め手で発覚。
- **罠③: 正方重みに隠れた転置バグ** — 数値プローブを正方形状で書いたため転置規約の誤りが素通りし、「1番速い run」が実は壊れていた。非正方形状のプローブで検出し、その run は集計から除外した。
- 一般化した対策は3点セット: **(1) 定常判定を計測結果に埋め込む、(2) 最適化経路の有効/無効を fail-fast + 記録で顕在化する、(3) 外部 primitive は縮退ケース+非正方形状の数値プローブで計測前に検証する**。
- この3点を JSON 成果物(`steady_state_valid` / `*_active` / `probe deltas`)として残せば、「速くなった」という主張を第三者が数字だけで監査できる。

:::note warn
研究用コードの実験ログです。数値は自作モデル・A100・特定構成での実測であり、一般化はできません。ただし「罠」の構造は環境非依存です。
:::

---

## 前提: 何を最適化していたか

対象は金融特化学習中の自作 Recurrent-Depth Transformer(98.6M、MoE FFN、ACT 適応計算)。ACT カリキュラム × torch.compile の両立、MoE の grouped GEMM 化、fused AdamW などを順に入れ、学習ベンチを約 2.3 倍にした。個々の最適化の詳細は過去記事([ACT×compile](https://qiita.com)、[grouped MoE](https://qiita.com))に譲り、本記事は**測定の失敗と対策だけ**を扱う。

方針として、各最適化は「ベンチ → 実装 → 回帰テスト → 品質評価」を1項目ずつ回し、同一 checkpoint・同一バッチ・同一シードで前後比較した。**それでも3回測定を誤った。**

---

## 罠①: コンパイル代が計測区間に漏れる

torch.compile 対応の最初の A100 計測(20 steps、warmup 3)はこうだった:

```text
eager  : 2,936 tok/s
compile: 1,325 tok/s   ← 2.2 倍遅い?
```

原因はモデルの動的制御フロー。ACT の早期終了で実行ループ数がステップごとに変わると、Dynamo は**ループ数ごとに別グラフをコンパイル**する。warmup 3 ステップでは全バリアントをコンパイルし切れず、**8 個分のコンパイル時間が計測区間に混入**していた。52,000 ステップの本番では一度きりのコストなのに、20 ステップで割れば「compile は遅い」に見える。

**対策: 定常判定をデータに埋め込む。** Dynamo counter を warmup 終了時と計測終了時に読み、グラフ生成数を区間別に記録した:

```text
compile: 10.436s  39250.4 tok/s  graphs=8 (warmup=8, measured=0)
```

`measured_unique_graphs != 0` の結果は定常速度として**扱わない**(JSON に `steady_state_valid: false` が付く)。warmup は動的挙動が一巡する長さ(ここでは ACT 閾値ランプ全体)を取る。修正後の定常値は **1.075 倍速**で、当初の 0.45 倍は完全に測定の虚像だった。

> 教訓: 「warmup を置いた」は定常の証明にならない。**定常だったかどうかを結果自体が主張できる**形式にする。

## 罠②: silent fallback — 「変化がない」は正常ではない

MoE の expert ループを PyTorch native の `grouped_mm` に置き換え、`--grouped_moe` を付けて計測した最初の結果:

| 指標 | ベースライン | --grouped_moe |
|---|---|---|
| tok/s | 38,054 | 38,845(+2%) |
| peak VRAM | 3,137.0 MiB | **3,137.0 MiB(完全一致)** |
| max loss delta | 0.00154114 | **0.00154114(8桁一致)** |

「効果なしか」と読みそうになるが、これは逆に**ありえない結果**だ。カーネルを本当に置き換えたなら、bf16 の丸めで loss は微妙に動き、メモリレイアウトの変化で peak も動く。全指標の完全一致は「**同じ計算をもう一度測った**」ことの証拠だった。

実際、有効化判定の1条件(`x.dtype == bf16`)が autocast 下の fp32 残差ストリームで常に倒れ、実装は静かに旧ループへフォールバックしていた。フォールバック自体は堅牢性のための正しい設計だが、**ベンチマークにとっては毒**になる。

**対策: 要求と実態を分離して顕在化する。**

- 明示的に要求された最適化が不活性なら、fallback せず**理由コード付きで即エラー**(`reason=dtype_not_bfloat16` など)
- 各計測結果に `grouped_moe_active` を記録し、「要求 = 実行」を JSON レベルで検証(`request_valid` フラグ)

修正後の実測は **1.98〜1.99 倍**。「変化なし」の正体は 2 倍の改善だった。

> 教訓: フォールバック付き最適化のベンチは、**「測りたい経路が動いたか」を測定結果から判定できる**ようにする。そして「何も変わらない」は run 間ノイズより先に fallback を疑う。

---

## 罠③: 正方重みがバグを隠す

罠②の対策として、計測前に実 API を参照実装(`F.linear` のグループ分割)と突き合わせる数値プローブを導入した。ところが**最初のプローブは正方形状で書いてしまい**、転置規約の誤りが素通りした。正方行列では `W` と `Wᵀ` が同じ形状のため、shape エラーにならず「それらしい数値」が出てしまう。

その状態で出た「79,396 tok/s(最速)」の run は、first loss が 14.60 → 13.97 へ不自然に動いていた。プローブを**非正方形状(in=16, out=24)+ 空 expert(counts=[3,0,5])**に書き直すと転置の誤りが即座に検出でき、修正後は全 delta 0.0(bit 一致)、loss も legacy と 0.0003 未満で一致。壊れていた run は性能集計から除外した。

> 教訓: 数値プローブは**対称性がバグを隠せない形状**で書く。正方行列・単位的なスケール・均等ルーティングは、転置・スケール・境界の誤りをすべて素通しにする。非正方+縮退ケース(空グループ、境界未満の行数)を必ず含める。

## 一般化: 観測可能性チェックリスト

3つの罠は独立に見えて、根は同じ — **ベンチマークが「数字」だけを返し、「その数字が主張を支える条件が成立していたか」を返していなかった**。対策を成果物(JSON)の必須フィールドとして一般化するとこうなる:

```jsonc
{
  "runtime": { "python": "...", "torch": "...", "gpu": "...", "dtype": "..." },
  "results": [ { "mode": "...", "tokens_per_second": ...,
                 "measured_unique_graphs": 0,     // 罠①: 定常判定
                 "optimization_active": true } ], // 罠②: 経路の実態
  "probe": { "output_max_abs_delta": 0.0,         // 罠③: 計測前の数値検証
             "grad_max_abs_delta": 0.0 },
  "steady_state_valid": true,                     // 上記の AND(機械判定)
  "request_valid": true
}
```

運用ルール:

1. **`steady_state_valid` が false の結果は比較に使わない**(人間の判断ではなくフラグで弾く)
2. **要求した最適化が不活性なら fail-fast** — silent fallback は本番の堅牢性としては可、ベンチ・明示要求時は不可
3. **数値プローブは計測前に自動実行**し、非正方形状+縮退ケースを含め、delta をそのまま成果物に残す
4. 複数 run の**中央値**で判定し、外れ値 run は理由(プローブ失敗・fallback 検出)とともに除外を記録する

このリポジトリでは、この形式の JSON がベンチごとに自動生成され、「約2.3倍」という主張の各段(compile 1.075×、grouped MoE 1.99×、fused AdamW 1.162×)を数字だけで遡って監査できる。

## まとめ

| 罠 | シグナル | 対策 |
|---|---|---|
| ① コンパイル代の混入 | 短い計測で「compile が遅い」 | グラフ生成数を warmup/計測区間で分離、`measured=0` を合格条件に |
| ② silent fallback | 全指標がベースラインと完全一致 | fail-fast + `*_active` の記録、「変化なし」をまず疑う |
| ③ 対称性がバグを隠す | 「最速 run」で loss が不自然に移動 | 非正方形状+縮退ケースの数値プローブを計測前に必須化 |

「速くならない」のは仕切り直せばいいが、「正しく測れていない」ことに気づかないと、**誤った結論(compile は不向き / grouped GEMM は効果なし / 壊れた run が最速)をロードマップに書いてしまう**。測定の観測可能性は最適化そのものと同じ重さで設計する価値がある。
