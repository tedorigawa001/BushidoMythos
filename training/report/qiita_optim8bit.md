# 8-bit optimizer で学習メモリを削る — ほぼ無損失で 600MB 節約(実測)

LLM を**少ないリソースで学習**したいとき、まず効くのが **8-bit optimizer**。自作モデルで fp32 AdamW と比較したら、**loss はほぼ一致のままピークメモリ 600MB(19%)削減**できた。仕組みと実測を整理する。

:::note info
研究用コードの実験ログ。投資助言ではありません。
:::

---

## 背景:学習メモリの最大要素は「オプティマイザ状態」

モデル学習時の GPU メモリは、ざっくり4要素:

| 要素 | サイズ（params=P） |
|---|---|
| モデル重み | P × 2〜4 byte |
| 勾配 | P × 2〜4 byte |
| **オプティマイザ状態(Adam の m, v)** | **P × 8 byte(fp32)** ← 最大 |
| 活性化 | バッチ・系列長・深さ依存 |

Adam は各パラメータに **m(1次)と v(2次)** を fp32 で持つので **8 byte/param**。重みより重い。ここを削るのが 8-bit optimizer。

---

## 8-bit optimizer がやること

オプティマイザ状態(m, v)を **block-wise に 8-bit 量子化**して保持する(bitsandbytes の `AdamW8bit`)。

```
fp32 Adam:  m,v = 8 byte/param
8-bit Adam: m,v ≈ 2 byte/param   ← 1/4
```

ブロック単位で動的にスケールするため、**精度劣化はごくわずか**。bitsandbytes は **Dettmers らの「8-bit Optimizers」系の実装**(block-wise quantization + dynamic exponent)で、よく検証されている。**モデル重みは触らない**(推論量子化とは別物)。

---

## 実験:fp32 AdamW vs 8-bit AdamW

同一モデル(自作 98.6M)・同一データ(乱数バッチ)・同一シードで、**n_loops を固定して forward を決定化**し、両 optimizer を 50 ステップ回した。差が optimizer のみに由来するようにしてある。

```bash
pip install bitsandbytes
python training/exp_optim8bit.py --device cuda \
  --ckpt checkpoints/finance_a100_v2/phase1_final.pt \
  --steps 50 --batch_size 4 --seq_len 256
```

### 結果

| | final loss | peak メモリ | 時間 |
|---|---|---|---|
| fp32 AdamW | 11.2494 | 3236 MB | 15.5s |
| **8-bit AdamW** | 11.2470 | **2636 MB** | 14.0s |

- **ほぼ無損失**: 全ステップの loss 最大差 = **0.00379**(両者 11.25 に収束)。
- **ピークメモリ 600MB 削減(19%)**。
- 今回は **僅かに高速**(14.0 vs 15.5s)。ただし 50 step の短時間実験なので**誤差の可能性**があり、環境・bitsandbytes kernel・モデルサイズで変わる。

### 「600MB」の内訳が理論と一致

理論オプティマイザ状態: **fp32 789MB → 8-bit 197MB(= 592MB 削減)**。
実測の削減 600MB とほぼ一致 → **削減は完全にオプティマイザ状態由来**で、他(重み・勾配・活性化)は不変。狙い通り。

---

## いつ効くか（効果はモデルが大きいほど大きい）

削減量は **params に比例**する:

| モデル | fp32 Adam 状態 | 8-bit | 削減 |
|---|---|---|---|
| 98.6M（今回） | 789MB | 197MB | ~592MB |
| 520M | 4.2GB | 1.0GB | ~3.1GB |
| 1B | 8GB | 2GB | ~6GB |

- 今回 19% に留まったのは、**活性化(batch4×seq256×8ループ)がピークの多くを占める小モデル**だから。
- なお**今回の比較は fp32(amp なし)**。一般論として、**bf16 / gradient checkpointing で重み・活性化側を削るほど**、相対的にオプティマイザ状態の比率が上がり、**8-bit の価値が増す**(実験条件とは分けて読んでほしい)。
- 大きいモデルや memory-bound な設定ほど、**「載らなかったものが載る」**効きになる。

---

## 設計上の判断:推論量子化とは分けて考える

メモリ削減には INT4/INT8 の**重み量子化**もあるが、あれは**推論**(または QLoRA)の話。混同すると危険なので分離した:

| | 8-bit optimizer | INT4/INT8 量子化 |
|---|---|---|
| 圧縮対象 | オプティマイザ状態 | モデル重み |
| フェーズ | **学習** | 推論 / QLoRA |
| 品質リスク | ほぼ無し | 小〜中（要検証） |

今回は**学習トラック単独**。`--optim8bit`で明示的に有効化し、CUDA/bitsandbytesが無ければ設定誤認を防ぐため即時エラーにする。resumeで設定が不一致ならmomentumをリセットして警告する。

## まとめ

| 項目 | 結果 |
|---|---|
| loss への影響 | ◎ ほぼ無損失(差 0.004) |
| メモリ削減 | ◎ 600MB(19%)= オプティマイザ状態を 1/4 |
| 速度 | ◯ 今回は僅かに高速(短時間実験・環境依存で誤差あり) |
| 効果のスケール | ◎ params に比例(1B で ~6GB) |
| コスト | ◎ フラグ1つ・自動フォールバック |

**「ほぼ無損失で学習メモリを削り、より大きなモデル/バッチを同じ GPU に載せる」** — 少リソース学習の定番の一手。**CUDA 環境ではまず試す価値が高い**最適化だ(bitsandbytes 依存・resume は同じ設定で、という運用上の注意はある)。
